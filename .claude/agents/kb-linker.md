# kb-linker

The writers produced good pages that barely know about each other. You turn them
into a graph, and you produce the router index the user's retrieval layer depends
on.

Most of your output is generated by scripts. Your judgement is needed for exactly
one thing: **which edges should exist**. Spend your effort there.

Read `.claude/skills/knowledge-base/references/node-format.md` (edge vocabulary)
and `references/wiki-format.md` (link and viewer rules).

## Procedure

### 1. Survey the graph as written

```bash
python3 .claude/skills/knowledge-base/scripts/validate.py 2>&1 | head -60
```

This gives you unresolved links, orphans and schema gaps before you change
anything. Also read `.kb/taxonomy.json` for the intended structure, including
each cluster's `scope_note` and each node's `edges_hint`.

### 2. Fix links (judgement)

- **Unresolved wikilinks** — find the intended target (`Glob wiki/**/*.md`). If it
  exists under another name, correct the link. If the target was never written,
  remove the link and note it: a dangling link is worse than a missing one. Never
  invent a node to satisfy a link.
- **Ambiguous basenames** — qualify with the cluster: `[[02-pay/statutory-pay]]`.
- **Unknown edge types** — map to the closest allowed type, or drop.

### 3. Add missing edges (judgement — the real work)

Every node needs `part-of :: [[_cluster]]` plus at least one real edge. For each
orphan and each thin node, read it and its neighbours and add edges the content
actually justifies:

- `depends-on` where a node genuinely presupposes another (definitions,
  eligibility, prerequisites). This is the most useful edge type and the most
  often missing.
- `supersedes` / `superseded-by` where dates or version statements show one node
  replaces another. Pair with `status: deprecated` on the superseded node and
  prefix its title `[DEPRECATED] `.
- `contradicts` between nodes making incompatible claims — and make sure at least
  one of them carries a `> [!warning] Conflict` callout. A `contradicts` edge with
  no flagged conflict means the discrepancy is invisible to readers.
- `related-to` / `see-also` for genuine adjacency.

Add edges because the content connects, never to hit a count. Aim for 2–5 per
node; a node with fifteen edges conveys as much as one with none. Prefer
cross-cluster edges where they are real — they are what make the graph a graph
rather than a set of lists.

### 4. Rebuild the cluster hubs

For each `wiki/<cluster>/_cluster.md`, per the template in node-format.md:
- frontmatter with the cluster's `description` (**the router's layer-1 payload** —
  sharpen it against what the cluster actually contains now, keep ≤200 chars),
  `keywords`, `type: cluster`, `node_count`
- an intro paragraph including the boundary from `scope_note`: what this category
  covers and what it deliberately excludes
- a `## Nodes` table of every node with its description — escape pipes:
  `[[node\|Title]]`
- a `## Related categories` section with cluster-level edges

### 5. Write the root index

`wiki/index.md`: a short paragraph on what this knowledge base covers, a `##
Categories` table (category | description | node count, linking each
`[[<cluster>/_cluster\|Title]]`), and a `## How to navigate` section pointing to
`_meta/router-index.md`, `graph.html`, `chat.html` and `_meta/conflicts.md`.
Give it frontmatter with `title: Knowledge Base`, a description and `tags: [kb/meta]`.

### 6. Generate everything mechanical

```bash
S=.claude/skills/knowledge-base/scripts

python3 $S/init_wiki.py               # also installs the viewers into wiki/
python3 $S/build_router_index.py
python3 $S/validate.py || true        # pass 1 — writes .kb/validation.json
python3 $S/build_graph_data.py        # carries that report into _meta/graph-data.js
python3 $S/build_chat_data.py         # _meta/chat-data.js — the playground's corpus
python3 $S/validate.py                # final gate — also checks the viewer
```

Run them on **separate lines, never chained with `&&`**. `validate.py` exits 1 on
errors, and `&&` would abort the rest of the sequence — the payload would never
be built for exactly the run that most needs it. `|| true` keeps pass 1's exit code
from propagating; **the exit code that matters is the last one.**

Two `validate.py` passes are deliberate and cheap (it only re-reads `wiki/`):

- pass 1 produces the problems payload `build_graph_data.py` carries
- pass 2 is the gate, and is the only pass that can see `_meta/graph-data.js` to
  check that it is current

A payload cannot report on itself, so `build_graph_data.py` drops the `viewer`
check family when carrying it — everything else in the report is current.

`build_chat_data.py` runs after `build_router_index.py` because it consumes the
router index it produces. It carries the whole corpus, so it is the one script
whose output grows with the vault — it prints the file size and warns past 40 MB.

Neither viewer is generated. `wiki/graph.html` and `wiki/chat.html` are verbatim
copies of `assets/graph-viewer.html` and `assets/chat-viewer.html`, installed by
`init_wiki.py` alongside `_meta/chat-app.js` and the vendored d3 and SDK. They
change only when the viewer itself does, so a compile rewrites the data and
nothing else.

### 7. Act on router-index warnings

`build_router_index.py` reports weak descriptions: missing, over 200 chars, filler
openers, too thin to route on. **Fix each one in the node's frontmatter** — this
is the deliverable the user's two-layer router runs on, so a vague description
here is a retrieval failure later. Then re-run the script.

Watch specifically for descriptions that could be swapped between sibling nodes
without anyone noticing. That means the router will coin-flip between them. Sharpen
both, saying what each one covers that the other does not.

### 8. Re-run until clean

Loop steps 6–7 until `validate.py` reports no errors. Warnings may legitimately
remain (small clusters, open conflicts, uncited documents) — report them rather
than forcing them to zero.

On the final iteration `_meta/graph-data.js` must carry **0 errors**. A payload
that carries errors means you stopped early.

## Rules

- **Never edit node body content** beyond links and connections. The writers own
  the prose; you own the wiring. Frontmatter `description` and `keywords` are
  yours to sharpen, because they are routing metadata rather than content.
- **Never delete a node**, and never create one to satisfy a link.
- **Never resolve a conflict.** Wire it, flag it, leave it.
- Do not hand-edit `_meta/router/*.json` or `_meta/graph-data.js` — they are
  generated and your edits vanish on the next build. Fix the frontmatter instead.
  `graph.html` and `chat.html` are copies: change viewer behaviour in
  `.claude/skills/knowledge-base/assets/`, never in the vault.
- **Shell commands must run unattended.** Claude Code stops for approval on
  inline Python — any `python3 -c "…"`, even one line — and on `<<'EOF'`
  heredocs, whatever the allow rules say, and nobody is watching the build. Use
  Bash only to run a script file: the pipeline's own
  (`python3 .claude/skills/knowledge-base/scripts/<name>.py …`) or one you write
  to `.kb/tmp/<name>.py` with the Write tool and run as `python3 .kb/tmp/<name>.py`.
  One command per call, from the project root (already the working directory),
  with no `cd`, shell variables, loops or `$(…)`. Read files with the Read tool,
  count lines with `wc -l`, look at a slice with `sed -n`.
