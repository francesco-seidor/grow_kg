Claude-Agents — Knowledge-Base Setup

A knowledge-base compiler: turns a folder of raw documents into a categorized, linked markdown knowledge graph, a wiki/graph.html d3 viewer, a wiki/chat.html router playground, and a two-layer retrieval router index. This page is a static workflow map of the .claude/ setup — every decision, retry, fan-out wave and loop that actually happens when a command runs — generated by reading the setup, not by running it.

static snapshot · no server · .claude/ untouched

You have a messy pile of documents.
This turns them into a small, tidy library — and then you can just ask it questions.

1 You drop papers in a box

Word documents, text files, notes — any structure of folders. The machine never writes on them.

2 Six little helpers build the library

They read everything, decide what rooms the library needs, write the pages, and put up signs.

3 You ask it questions

It walks to the right page and answers from it — and always tells you which page it used.

    Promises it keeps

    These are the rules it will not break, no matter what.

    • ✓It never writes on your papers. Your originals come out exactly as they went in.
    • ✓It never makes up facts. If a number, date or rule isn't in your papers, it will not appear in the library.
    • ✓If two papers disagree, it tells you. It won't quietly pick a winner and hide the other one.
    • ✓It never throws a page away. Old pages get stamped "out of date" and stay.
    • ✓Nothing goes missing quietly. Every single paper is either used, or listed as "couldn't open this one".
    • ✓Every answer comes with a receipt. You always get told which page the answer came from.
    • ✓The two web pages are always rebuilt, never patched. The map, the question window and the take-away box all come from the pages themselves — so they cannot drift away from what the library actually says.

    Folder contract

    Four folders, four jobs. wiki/ is the deliverable; .kb/ and exports/ sit outside it and are both gitignored, so neither staging state nor a generated distribution ever lands in the knowledge base. Nothing but the compiler writes markdown into wiki/ — every .md under it (bar _meta/) is scanned as a node, which is exactly why the export lives elsewhere.

    raw_assets/Input documents. .md .markdown .txt .docx .doc .rtf .xlsx .xlsm .csv — READ ONLY, never modified by the pipeline.
    →
    .kb/Pipeline state — extraction, digests, taxonomy, validation. Fully disposable / regenerable, but expensive to rebuild.
    →
    wiki/The compiled knowledge base — nodes, clusters, the router index, graph.html and chat.html with their data under _meta/. This is what you keep.
    →
    exports/Generated distributions of wiki/ — currently the Claude Project export. On demand, never from /kb-build.

    A fifth folder, visualizer/, is documentation rather than pipeline: this page, plus knowledge_graph.md — a portable README you copy next to a finished wiki/ so any Claude session can route and answer from it with no .claude/ setup at all.

    Commands & modes

    Every command is a thin entry point into one knowledge-base skill, run in a different mode.

    /kb-buildMode 1

    Full compile of everything in raw_assets/.

    • Runs all 6 stages in order, fan-out waves of up to 6 batches at a time.
    • Above 100 documents: stops and asks the user to confirm before fanning out.
    • Orchestrator sanity-checks .kb/taxonomy.json before Stage 3 — a bad taxonomy costs the entire writer stage.
    /kb-updateMode 2

    Incremental recompile of what changed in raw_assets/ (sha256-based).

    • Digests only new/changed docs; writer rewrites only affected clusters.
    • kb-architect runs incrementally — never renumbers/renames existing clusters; structural changes are proposed, not auto-applied.
    • Linker + auditor still run in full. Stops early if nothing changed.
    /kb-ask <question>Mode 3

    Answer from wiki/ only, routing through the two-layer index.

    • Never touches the 6-stage pipeline or raw_assets/ — reads wiki/_meta/router/*.json directly.
    • Always cites node path(s); never fabricates specifics.
    • Reports if nothing covers the question, or if routing landed wrong.
    /kb-auditMode 4

    Validation, coverage gaps, conflicts, staleness, router readiness.

    • Launches kb-auditor directly — the only command that names a specific agent.
    • Checks validation, coverage, conflicts register, staleness, router readiness.
    • Fixes mechanical defects only; factual issues go to a "needs a human decision" list.
    /kb-export-projectMode 5

    Export wiki/ as a Claude Project: an instruction prompt plus per-cluster knowledge bundles.

    • Runs on an already-compiled wiki, read-only — derives entirely from frontmatter and the router index.
    • Not a pipeline stage: it duplicates the base into a second format, so /kb-build never runs it.
    • A snapshot — --check exits 1 once it has gone stale; re-export after every build or update.

    Setup

    Optional but recommended, once. Creates .kb/venv with mammoth (preserves Word heading styles) and pyyaml. Without it, extraction falls back to a bundled dependency-free docx reader that keeps headings, lists and tables but loses inline bold/italic. Spreadsheets (.xlsx .xlsm .csv) become one table per sheet via xlsx2md.py, and a spreadsheet beside a same-named Word document is a companion — reported, not compiled twice. PDF and PowerPoint are out of scope — they are reported as unsupported rather than silently skipped.

    python3 .claude/skills/knowledge-base/scripts/bootstrap.py

    Two third-party bundles are vendored and committed under .claude/skills/knowledge-base/assets/vendor/, each with a .sha256 the build verifies: d3 v7 for graph.html and an IIFE bundle of the Anthropic JS SDK for chat.html. A compile must never silently reach the internet. init_wiki.py copies both into wiki/_meta/vendor/ beside the viewers that load them, checking the digest on the way. If a bundle is missing the page falls back to a CDN <script src> and needs the network — validate.py reports the missing copy as a warning.

    The Claude Project export

    Uploading wiki/ raw throws away everything the compile produced — the taxonomy, the router descriptions, the typed edges, the conflict flags, the deprecation markers — and leaves the Project doing undifferentiated search over prose. build_project_export.py projects the vault into the two halves a Project actually has instead: an instructions field carrying both router layers, and uploaded files whose sections are anchored at ## <node-id> — the same id the instructions name, so "open 02-expenses-and-travel.md and find ## 02-expenses-and-travel/expense-limits" is an instruction it can follow.

    It lives outside wiki/ and the script refuses --out paths inside the vault: every .md under the vault bar _meta/ is scanned as a node, so an export written inside would fail validate.py on every bundle and pollute the router index with phantom nodes.

    TierInline in the instructions
    fullcategories + every node with its description and alternate terms
    standardcategories + every node with its description
    clusterscategories only; the Project is directed to read 00-INDEX.md before answering anything

    The script emits the largest tier that fits --max-chars (default 30 000, a conservative budget rather than a claimed platform limit); --tier forces one. 00-INDEX.md always carries the complete index at full fidelity regardless of tier, so degrading the inline index never loses information. Below roughly 5k chars no tier fits — the grounding contract, routing protocol and answer rules are fixed prose, and the script says so rather than silently trimming them.

    In the bundles, wikilinks become Alias (node id), ## Connections becomes type :: id, conflict callouts are preserved verbatim, and deprecated nodes ship with a banner naming their successor — never dropped, matching the never-delete-a-node invariant. Guarantees: every node in the index appears in exactly one bundle, every node in a bundle appears in 00-INDEX.md, no [[wikilink]] survives, nothing is written inside wiki/.

    In plain words: the question window, wiki/chat.html. Every dial that decides which page the library picks for a question is on this one page, so you can turn them and see what happens — including a free keyword-matching mode that costs nothing to compare against.

    Why it exists

    The router has no scorer. /kb-ask says "score the categories, keep the runners-up, have a floor" — but how many clusters layer 1 keeps, how many nodes layer 2 keeps, what the floor is, and which model does the scoring are all unspecified, so there is nothing to tune. references/router-index.md specifies the index and then stops at pick(query, candidates). This page is that pick, with every parameter exposed and a trace under every answer.

    The page is a verbatim copy of assets/chat-viewer.html, installed by init_wiki.py together with assets/chat-app.js and the vendored SDK. Only its corpus is rebuilt per compile, by build_chat_data.py — the layer-1 catalog, every layer-2 entry and the full body of every node, arriving as _meta/chat-data.js. No server, no npm, and it never fetches: everything loads as a classic <script src> sibling, which works from file:// where fetch() does not. Unlike the graph payload, bodies are never truncated: a node with no body cannot be answered from, so --max-total-mb (default 40) only warns. With no corpus beside it, the page says which command to run.

    Three retrieval modes

    The baseline is the point: an LLM router that cannot beat keyword matching on your vault is not earning its tokens.

    ModeWhat it doesCost
    two_layerScore the catalog → keep top N clusters over the L1 floor → one call over the union of their nodes → keep top M over the L2 floor → answer3 calls
    flatOne scoring call over every node description; skips layer 1 entirely. The control — it tells you whether layer 1 is helping or hurting2 calls
    bm25Okapi BM25 over the pre-joined embedding_text, in the browser. The free floor1 call (answer only)

    Layer 2 scores the union of the kept clusters in a single call. Scoring each cluster separately would produce numbers from different contexts, and ranking across them would be meaningless.

    Flat-mode guard: over flat_max_input_tokens (default 60 000) or 2000 candidate ids the page refuses and explains rather than truncating. A baseline that quietly drops half the corpus is not merely wrong, it is confidently wrong.

    Floors

    Two of them — picking a cluster and picking a note are different decisions with different costs of being wrong. Defaults: L1 0.25, L2 0.45.

    The model is asked for a score per candidate and is never told the floor or the keep-count: the moment it knows the threshold it games it, and you lose the ability to move the floor without re-prompting. The page applies clamp to 0–1 → dedupe by key → sort desc → truncate to keep → apply floor. The floor comes last on purpose; applied earlier, a below-floor candidate could still occupy one of the keep slots.

    BM25 floors are relative (cut = floor × top score), because BM25 scores are unbounded and corpus-dependent. Normalising against the top hit means the winner always scores 1.0 — so raising the floor in BM25 mode prunes runners-up and never the winner. The only BM25 refusal is a query where no term matches anything, and the stage note in the trace says so.

    Below the floor

    What happens when nothing clears it. escalate is the one that answers the question you actually have while tuning: it separates "the cheap router was the problem" from "the content isn't there".

    SettingBehaviourExtra spend
    refuse (default)No answer call. Names the nearest misses and diagnoses the gapnone
    answer_anywayAnswers from the top candidates, flagged low-confidence in both the answer and the trace1 call
    widenRetries layer 2 once at keep × 2, floor × 0.5, reusing layer 1's scores1 call
    escalateRe-runs the deciding layer on a better model at high effort1 call
    bm25_rescueFalls back to keyword matching over the whole vault — catches the classic LLM-router miss: a rare proper noun that appears in no description1 call

    Diagnosis on every refusal

    The /kb-ask rule "say whether the gap is missing content or a weak description", made mechanical. This is the only part of the page that improves the wiki rather than just querying it.

    CodeMeansFix
    missing_contentThe right cluster exists, nothing in it answersWrite the note
    missing_cluster_or_weak_descriptionsNothing cleared layer 1Add a cluster, or say in the descriptions what they cover
    overlapping_descriptionsTop two clusters within 0.05 — the most valuable of these, and invisible from any single answerFix the taxonomy boundary, not the wording
    overlapping_nodesTop two notes within 0.05Merge them, or sharpen the boundary
    no_keyword_matchBM25 only: no query term appears anywhereTry the two-layer router — it matches meaning, not words

    Models, effort and caching

    A per-layer model, so a cheap router can feed an expensive answer. Every request is built by one function, so illegal combinations cannot be sent: an unlisted effort is dropped, thinking is shaped by the model family, and sanitize() repairs stored presets on load and save — a preset written before a model changed degrades with a note instead of 400ing.

    Modeltemperatureeffortthinkingmin cacheable prefix
    claude-opus-5400low–maxadaptive512
    claude-opus-4-8400low–maxadaptive1024
    claude-sonnet-5400low–maxadaptive1024
    claude-haiku-4-5allowed400budget_tokens4096
    claude-fable-5-1400low–maxalways on — omit512

    There is no temperature control, deliberately. It is removed API-wide on current models; a slider would only produce 400s. effort is the equivalent lever. answer.model: "none" is retrieve-only — no synthesis call, which makes retrieval tuning free and the whole page exercisable with no API key.

    Caching is static-first: system block 1 is the frozen instructions with no breakpoint, block 2 is the candidate list carrying cache_control, and the question goes last. auto attaches the breakpoint only when the block clears that model's minimum — do the arithmetic first: a six-cluster catalog is roughly 500 tokens, and Haiku 4.5, the natural cheap layer-1 router, has the highest minimum of any current model at 4096. The place you would instinctively cache is the place it provably cannot fire. Where it pays is layer 2 on a real vault, and the answer synthesiser's node bodies across turns. Candidate blocks are built from slug/title/description/keywords only and sorted by identifier — never by serialising the router JSON, which carries a fresh generated timestamp on every rebuild and would invalidate the cache each time.

    Two different confidences

    content_confidence comes from a node's frontmatter and is the compiler's confidence in the content. match_score is the router's confidence in the match. They are named apart at the data layer so the UI cannot render them in one column. A content_confidence: low note can still be the right answer — it shows as a caveat, never a demotion, and the answer prompt is told to surface it.

    Storage, the key, and feeding settings back

    Settings, named presets, a 300-entry run log and (only if you tick "remember") the API key live in localStorage, namespaced by the router index's content_hash so two vaults on one machine keep separate settings.

    file:// local storage is unreliable — Safari blocks it, and Chrome shares one bucket across all file:// pages. Every read and write is wrapped, falling back to memory with a visible banner. Two ways out: Export settings / Import settings (a JSON file, never containing the key), or serve the folder properly with cd wiki && python3 -m http.server.

    The key is held in memory for the session: never baked into the generated page, never written to an exported settings file, never put in the run log, never printed. A redact() pass strips anything matching sk-ant-[A-Za-z0-9_-]{8,} from every string reaching the trace or the log, as insurance against an SDK error echoing a header. The page calls api.anthropic.com directly with dangerouslyAllowBrowser: true.
